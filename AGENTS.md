# AGENTS.md

Руководство для разработчиков и ИИ-ассистентов, которые продолжают развивать
**3xbot** — бота нейрофотосессий для Telegram, ВКонтакте и MAX.

Этот файл должен помогать быстро и безопасно вносить изменения в продукт. Не
описывайте здесь историю создания проекта, внутренние рассуждения или то, как
был подготовлен репозиторий. Описывайте то, что нужно знать следующему
разработчику: поведение бота, архитектуру, контракты между модулями, риски и
правила проверки.

## Продукт

3xbot принимает фото пользователя в мессенджере, продаёт доступ к генерациям
через ЮKassa и создаёт 4 креативных AI-портрета через Replicate
`openai/gpt-image-2`.

Основной пользовательский сценарий:

1. Пользователь отправляет `/start`.
2. Бот показывает баланс и просит выбрать пол.
3. Если на балансе нет генераций, бот предлагает тарифы и создаёт платёж.
4. После успешной оплаты бот начисляет генерации и просит фото.
5. Пользователь отправляет фото.
6. Бот списывает 1 генерацию, выбирает 4 случайных стиля и генерирует 4 фото.
7. Бот отправляет результат и предлагает прислать ещё фото.

Один Python-процесс обслуживает все включённые платформы через long polling.
Webhook не используется: новые сообщения и статусы платежей бот получает
регулярным опросом API.

## Архитектура

```
bot.py        — точка входа, long polling Telegram/VK/MAX, платформенные каналы,
                загрузка .env, фоновый polling платежей
dialog.py     — общая логика диалога и FSM; не зависит от мессенджеров
generator.py  — генерация изображений через Replicate HTTP API
styles.py     — каталог стилей и английские prompt'ы для gpt-image-2
db.py         — SQLite: пользователи, баланс, подписки, платежи
payments.py   — ЮKassa: тарифы, создание платежа, проверка статуса
notifier.py   — отправка уведомлений пользователю по user_key
```

Зависимости намеренно минимальные: `requests` и `Pillow`. SDK мессенджеров,
Replicate и ЮKassa не используются, чтобы поведение интеграций оставалось
явным и одинаково контролируемым.

## Центральный контракт: channel

Вся продуктовая логика диалога живёт в `dialog.py` и вызывается так:

```python
dialog.handle(user_key, channel)
```

`channel` — платформенный адаптер из `bot.py`. Он обязан поддерживать:

- `send_text(text)`
- `send_buttons(text, options)` — `options: list[(payload, label)]`
- `send_styles_menu(text, options)` — исторический метод, сейчас не вызывается
- `send_photos(urls, caption)`
- `incoming.text` — входящий текст или `""`
- `incoming.photo_bytes()` — байты входящего фото или `None`

Если меняется сценарий диалога, сначала меняйте `dialog.py`. В `bot.py`
добавляйте только платформенную механику: отправку, получение, загрузку фото,
callback-кнопки и маршрутизацию уведомлений.

## Состояние и ключи пользователей

FSM диалога:

- `S_GENDER` — бот ждёт выбор пола.
- `S_PHOTO` — бот ждёт фото для генерации.

Состояние FSM хранится в памяти процесса в `dialog._sessions` и сбрасывается
при перезапуске. Баланс, подписки и платежи хранятся в SQLite (`bot.db`) и
переживают перезапуск.

`user_key` всегда имеет формат:

- `tg:<chat_id>`
- `vk:<peer_id>`
- `max:c<chat_id>`
- `max:u<user_id>`

Для MAX префикс `c` или `u` обязателен: он показывает, куда отправлять
уведомление после оплаты — в чат или конкретному пользователю.

## Платежи

Платежи создаются в `payments.create_payment()`, сохраняются в `db.create_payment()`
и затем проверяются фоновым `payment_poller()` в `bot.py`.

При статусе `succeeded` бот:

1. Начисляет тариф через `dialog._grant()`.
2. Помечает платёж успешным в SQLite.
3. Переводит пользователя в `S_PHOTO`.
4. Отправляет уведомление через `notifier.notify()`.

При статусе `canceled` бот помечает платёж отменённым.

Для коммерческого запуска в РФ проверьте требования 54-ФЗ: текущая реализация
не отправляет объект `receipt` в ЮKassa.

## Генерация

`dialog._run_generation()` списывает 1 генерацию перед вызовом Replicate. Если
генерация падает, списание возвращается через `db.add_credits(user_key, 1)`.
Это обязательное поведение: пользователь не должен терять оплаченный баланс
из-за сетевой ошибки, модерации модели или сбоя Replicate.

`generator.py`:

- нормализует входное фото через Pillow;
- передаёт фото в Replicate как data URL;
- запускает параллельные prediction-запросы;
- возвращает URL успешных изображений;
- бросает `GenerationError`, если не удалось получить ни одного результата.

В `generator.py` используется `moderation: "low"`. Не повышайте значение до
`"auto"` без отдельной проверки: модель часто ложно отклоняет обычные портреты
ошибкой E005.

## Кнопки и payload

Платформы по-разному передают нажатие кнопки:

- MAX inline-callback отправляет `payload`, например `buy:sub` или `female`.
- Telegram и VK reply-кнопки отправляют видимую подпись, например
  `🔥 Подписка — 499 ₽/мес`.

Поэтому парсеры выбора в `dialog.py` должны распознавать оба варианта:

- `_parse_gender()`
- `_parse_plan()`

Если добавляете новую кнопку, обновляйте парсер так, чтобы она работала во
всех трёх мессенджерах.

## Переменные окружения

`.env` загружается в `bot.py` через `load_env()`. Секреты нельзя читать на
уровне импорта в модулях, которые импортируются до `load_env()`.

Правило: токены и ключи в `generator.py` и `payments.py` читаются в момент
вызова функции, а не при импорте модуля.

Секреты и локальные данные не коммитятся:

- `.env`
- `bot.db`
- `__pycache__/`
- `.venv/`
- `.ruff_cache/`

## Правила изменений

- Пользовательские тексты, комментарии и документация — на русском.
- Prompt'ы для gpt-image-2 — на английском.
- Не добавляйте SDK платформ без сильной причины: текущая архитектура держится
  на прозрачных HTTP-интеграциях.
- Не дублируйте диалоговую логику в платформенных классах.
- Не роняйте polling-цикл из-за одного пользователя; обработчики должны
  оставаться защищены `_safe_handle`.
- Не меняйте формат `user_key` без миграции `db.py`, `notifier.py` и платежей.
- Не убирайте возврат генерации при ошибке.
- Не добавляйте секреты, реальные токены, локальные базы или логи в Git.

## Проверка

Во время работы проверяйте только изменённые Python-файлы:

```bash
ruff check path/to/changed.py
python3 -m compileall -q path/to/changed.py
```

Это офлайн-проверка: она не запускает бота и не обращается к Telegram, VK, MAX,
Replicate и ЮKassa. Проверку оплаты и диалога ниже она не заменяет.

Перед коммитом выполните финальный набор целиком:

```bash
ruff check .
python3 -m compileall -q .
git diff --check
```

Если меняли оплату, вручную проверьте:

- создание платежа;
- сохранение `payment_id` в SQLite;
- переход pending → succeeded;
- начисление нужного тарифа;
- уведомление пользователя после оплаты.

Если меняли кнопки или диалог, проверьте, что один и тот же выбор работает как
по payload, так и по текстовой подписи кнопки.

## Документация для агентов

`AGENTS.md` должен оставаться практическим файлом сопровождения продукта. В
нём нужны:

- что делает бот;
- как устроены основные модули;
- какие контракты нельзя ломать;
- как запускать и проверять изменения;
- какие интеграционные нюансы легко сломать.

В нём не нужны:

- история разработки;
- описание того, что репозиторий учебный;
- маркетинговые формулировки;
- длинные пересказы README;
- временные заметки, которые устареют после ближайшего коммита.

`CLAUDE.md` не должен дублировать эти инструкции. Для Claude Code он должен
импортировать общий файл одной строкой:

```text
@AGENTS.md
```
